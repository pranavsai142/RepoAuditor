### [warning] Numstat oracle test is circular and cannot catch binary→0

- file:line
  - `tests/test_extract.py:15-48`
  - `src/repoauditor/extract.py:93-109`
- description
  The Just-Go gate is `parser ≠ git log --numstat`. `test_extract_matches_git_oracle` compares commit counts to an independent `git rev-list --all --count` (good) but compares volume to `_oracle_numstat_sum`, which re-parses the **same** `LOG_ARGV` output with the same `\x1e` / tab / `'-'` rules. Even if a binary file were present, coercing `'-'` to `0` on the commit row would not fail the assertion: both sides add `0` to the sum (`c.additions or 0` vs `continue` on `'-'`). The locked rule is “binaries stay `null`, not `0`.” This test never inspects `FileChange.additions is None` / `is_binary`.
- suggestion
  Assert per-file and per-commit nullness against a real binary blob. Independently sum `git diff-tree --numstat` (or `git show --numstat --format=`) per hash rather than cloning `_parse_log`.
- status: open

### [warning] “rank does not call git” test would miss a regression through extract

- file:line
  - `tests/test_rank.py:36-45`
- description
  Implementation is clean: `rank.py` and `patterns/detect.py` do not import or invoke git; `cmd_flag` only reads JSON. The test is not. It monkeypatches `repoauditor.gitcmd.run_git` *after* a first `cmd_rank` has already written derived files, so the second call never assimilates. `extract.py` binds `run_git` at import time (`from repoauditor.gitcmd import run_git`); a future `cmd_rank` → `extract_repo` would still use that binding and the test would stay green. There is no `flag` equivalent at all.
- suggestion
  Patch `repoauditor.extract.run_git` (and/or `extract_repo`) *before* the only `cmd_rank`/`cmd_flag` invocation, with derived deleted so assimilate also runs under the patch.
- status: open

### [warning] git wrapper decodes as locale text and inherits GIT_DIR

- file:line
  - `src/repoauditor/gitcmd.py:39-45`
  - `src/repoauditor/extract.py:112-119`
- description
  Extract locks `i18n.logOutputEncoding=UTF-8` but `subprocess.run(..., text=True)` decodes with the process locale, not `encoding="utf-8"`. `git show --patch` used for `patch_id` is file content, not log encoding; a latin-1 or binary-as-text blob raises `UnicodeDecodeError` and aborts the whole repo extract (not converted to `patch_id=None`). Inherited `GIT_DIR` / `GIT_WORK_TREE` override `git -C <repo>`, so extract can silently read the wrong repository. No fixture exercises either path.
- suggestion
  Force `encoding="utf-8", errors="surrogateescape"` (or bytes for `show --patch`). Unset `GIT_DIR`, `GIT_WORK_TREE`, and `GIT_INDEX_FILE` in the child env.
- status: open
